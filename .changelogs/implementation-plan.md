**Component 3 — Defect-Class Preflight.** The ticket asked why a two-phases-old `PROCESS_LEARNINGS.md` receipt-path lesson recurred. Investigation gave a sharper answer than "project memory failed": the suite **already had** two mechanisms aimed at that class — STRICT RULE 28 and STRICT RULE 27's dual cross-reference — and both fired correctly (`receipt_status: not_found`); the phases were marked `**COMPLETED**` anyway. The gap was never detection. It was that nothing consulted already-diagnosed classes at *drafting* time, when the correct acceptance criterion could still be written into the fix. `scripts/plan/defect_classes.py` holds six suite-global classes, each traceable to a closed ticket, a STRICT RULE, or a real corpus finding; project-local classes are read from the workspace's own `PROCESS_LEARNINGS.md`. Matching is deliberately generous (a false positive costs one extra acceptance criterion; a false negative costs a repeated lesson) and exposes `matched_signals` so a spurious match can be discarded rather than silently accepted. Strictly a drafting-time aid — adds no runtime gate to `/execute-build`, `/nodelete` Pillar 6, or `phase_status.py`.

**Engines built** (`scripts/plan/`, per role.md's code-authority clause — ticket-instrumental, test-covered, suite green): `findings.py` (audit parser), `remediation_ledger.py` (CLI), `defect_classes.py` (registry + preflight CLI), plus `LedgerReporter` added to the existing `reporter.py`. The scripts **enumerate and verify; they never draft** — mapping a finding to a corrective action is judgment and stays with the agent, the same division every other engine-backed workflow in this suite uses.

**Premise corrected during build, disclosed rather than absorbed**: the design asserted the audit findings shape "held across both sampled audits." True for the two recent ones, but the full persisted corpus is 68 audits spanning every scoring model this workflow has ever had, with the findings heading written ~20 different ways and **four** distinct item conventions (numbered/bulleted lists; `###` sub-headings; `- **Deduction:** N points` detail lists nested beneath those; and bare labelled paragraph lines like `**C1 — claim**` / `WEAKNESS 1 — claim`). The parser was hardened against all four, with explicit precedence, after live corpus runs surfaced 12 real false negatives across three separate conventions. Deductions parse in three formats including a unicode-minus parenthetical `(−12)`. This did not change the design — the positional-ID fallback existed precisely so no immutable audit needs retroactive editing — but it materially raised the robustness bar, and the design's "verified across two audits" claim was too small a sample to have supported the conclusion it was offered for.

**The engine's single most important correctness property**: `status: "ok"` with zero findings (a genuine zero — the Coverage Ledger model explicitly permits it) is reported as categorically distinct from `status: "no_findings_section"` (the section could not be located). Collapsing the second into the first would report "nothing to remediate" about a report full of Critical findings — Hallucinated Success in engine form. Enforced at three layers: the parser's status field, CLI exit code 2, and STRICT RULE 29's explicit HALT.

**Deliberately NOT built** (recorded so a later session does not quietly absorb it): no standalone `/remediate` workflow — the ticket's §4.4 deferral upheld, one consumer is not a generalization; no changes to Phase 5's audit semantics, scoring, Coverage Ledger, or Completion Marking; no auto-triggering and no auto-building (STRICT RULE 30); no changes to `/execute-build`, `/nodelete` Pillar 6, or `phase_status.py`; no retroactive editing of any persisted audit. The three May-2026 `## Audit Findings`-shaped reports and the six workstream audits correctly HALT with exit code 2 rather than being force-fit — a loud refusal on an unrecognized shape is the honest behavior, and guessing severity for an unlabeled finding was judged worse than halting.
